# Building

## Toolchain

MinGW-w64 GCC 14 (UCRT, POSIX threads, SEH) with CMake 3.21+ and Ninja. The
toolchain this is developed against lives at:

```
C:\Users\<you>\Documents\codeblocks-25.03mingw-nosetup\MinGW\bin
```

MSVC is not supported. The build has never been configured for it, and the
static-link path relies on GCC behaviour.

> Use **Ninja**, not "MinGW Makefiles" -- the Makefile generator trips over
> `sh.exe` when Git for Windows is on `PATH`. The presets already pick Ninja.

## Configure and build

```bash
cmake --preset debug
```

```bash
cmake --build --preset debug
```

```bash
ctest --preset debug
```

Everything runnable lands in `build/<preset>/bin/`: the executable, the layer
DLLs and the toolchain runtime side by side, so the build tree is also the run
tree.

## Presets

| preset           | build type     | layers | what you get |
| ---------------- | -------------- | ------ | ------------ |
| `debug`          | Debug          | DLL    | one DLL per layer, fast relinks, tests on |
| `relwithdebinfo` | RelWithDebInfo | DLL    | optimised with symbols, tests on |
| `release`        | Release        | static | a single self-contained `castlemist.exe`, ~7.6 MB |
| `minsizerel`     | MinSizeRel     | static | the same, optimised for size |
| `ci`             | RelWithDebInfo | static | warnings are errors, tests on |

The DLL split is the reason to develop in `debug`: editing one file in
`src/ui/` relinks `libcastlemist_ui.dll` and nothing else. Ship from `release`,
which archives everything into one binary with no DLLs to distribute.

## Options

| option | default | effect |
| ------ | ------- | ------ |
| `CASTLEMIST_SHARED_LAYERS`     | `ON`  | one DLL per layer instead of one static exe |
| `CASTLEMIST_BUILD_TESTS`       | `ON`  | build the unit suite |
| `CASTLEMIST_BUILD_TOOLS`       | `ON`  | build the CLI tools under `tools/` |
| `CASTLEMIST_BUILD_DOCS`        | `OFF` | add the `docs` target (needs Doxygen) |
| `CASTLEMIST_WARNINGS_AS_ERRORS`| `OFF` | `-Wall -Wextra -Werror` |
| `CASTLEMIST_EXTERNAL_DIR`      | `external` | where the third-party checkouts live |

Symbols are exported wholesale from the layer DLLs via
`WINDOWS_EXPORT_ALL_SYMBOLS`, so no source file carries `__declspec` annotations
and switching between the two layer kinds needs no code changes.

## The startup failure you will otherwise hit

MinGW's `libstdc++-6.dll`, `libgcc_s_seh-1.dll` and `libwinpthread-1.dll` are
not on a stock Windows `PATH`, and picking up a mismatched copy from some other
toolchain kills the process at startup with `0xC0000139`
(`STATUS_ENTRYPOINT_NOT_FOUND`) -- no window, no error box, no Windows Error
Reporting event, just a process that exits after about two seconds.

`castlemist_link_runtime()` in `cmake/Layers.cmake` handles this both ways:
static layers link the runtime into the exe, shared layers copy this compiler's
own runtime DLLs next to it after every build. If you build by hand rather than
through CMake, you have to do one or the other yourself.

To diagnose a binary that "exits doing nothing":

```bash
gdb -batch -ex run build/debug/bin/castlemist.exe
```

## Dependencies

All of them come from `external/` and are declared in `cmake/Externals.cmake`,
which fails at configure time by name if one is missing.
[`external/README.md`](../external/README.md) lists what belongs there and
where each library comes from -- the directory is not tracked in git.

Two of them are worth knowing about:

**libjpeg-turbo 3.x** dispatches sample precision at *runtime*, so the 8-bit
core references `j12init_*`/`j16init_*`: every file under `src/wrapper` has to
be compiled except `template.c`, the generator input, and `src/jstdhuff.c` is
include-only. Its `jconfig.h` / `jconfigint.h` / `jversion.h` are generated by
upstream's own CMake, which is not run here, so `external/jpegcfg/` supplies
them by hand and goes first on the include path.

**libwebp**'s include root is `src/`, not `src/webp/` -- headers are
`<webp/decode.h>`.

`src/media/stb_vorbis_impl.c` must be compiled **as C**; `stb_vorbis.c` does not
build as C++.

## Runtime files

None of these is required to start. Each unlocks a feature, and all of them are
things you generate from your own install -- see
[generating-data.md](generating-data.md).

| file | unlocks |
| ---- | ------- |
| `dumps/packfile/gw2_packfile.json`         | model, map and material extraction |
| `dumps/index/gw2_index.db`                 | type/container columns and fast filtering |
| `dumps/strs/textkeys.csv`, `strs_textbase.csv` | decrypting packed string records |
| `dumps/binaries/bink2w64.dll`              | cinematic playback |

The search climbs from the executable's directory towards the repository root,
so running out of `build/<preset>/bin/` finds them without any copying.
`GW2_BINK_DLL`, `GW2_TEST_INDEX_DB` and `GW2_TEST_TEMPLATE` override
individually.
