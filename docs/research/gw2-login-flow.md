GW2 client login architecture, RE'd from Gw2-64-disable-aslr.exe (imagebase 0x140000000). Establishes why a client-only emulator can't just "log in" and where the real gates are. Related: [[gw2-net-crypto]] (AuthSrv transport crypto).

**Three sequential gates (all must be satisfied for a working login):**
1. **STS (NCSoft Session Ticket Service) — credential validation.** The login form is a Coherent web/HTML view; email/password submit → `GameWeb::CBrowserBindings::BindStsRequest` (@str 0x141b7d9b0; assert "StsRequest without command" @0x141b7e878) → HTTPS call to NCSoft STS. **Credentials (e.g. test@test.com/test) are validated HERE, server-side — never checked locally in the client.** Returns a session ticket. This rides the pinned-cert HTTPS channel (StartCom root, see [[gw2-net-crypto]]).
2. **Portal (NCPlatform) — account/user info.** `GcPortal.cpp` (huge Pl* subsystem: PlUser/PlChannel/PlGroup/PlManager...). Error path str "Error retriving user info from Portal: %u:%u:%u:%u" @0x14191f538 → handler **sub_140246C30**. Uses the STS ticket.
3. **AuthSrv login transaction — plaintext MsgConn layer** (the one we can emulate). Login posted as async transaction obj (312B, vtable off_14191F5A8) by **sub_140246370**. Result handled by **sub_14023D350** ("Account login transaction result %u" @0x14191e990): **result u16 @struct+36 == 0 = SUCCESS**. Success path unpacks account GUID (struct+224, 20B → word_14266A120), session-key material, portal info, and the **character/world list** (struct+580 = 16*count entries, count @struct+576) into globals @0x14266Axxx, then dispatches the proceed-to-char-select event (sub_141061A00). result 1/1032 = other; result<=0x2A with bitmask 0x40004200080 = "Auth retry (%u)" via sub_140246370.

**STS/credential path detail (RE'd):** login form → `GameWeb::CBrowserBindings::BindStsRequest` (bind `sub_1409604C0`) → StsRequest handler `sub_140967A30` (GwPortalMsg.cpp; extracts web `command`+`protocol`) → `sub_140DC8C80` = builds an **HTTP request** (`POST <cmd> STS/1.0\r\n` or `HTTP/1.1`; InetMsgOut). So **STS is HTTP over the pinned-cert TLS channel** — and so is Portal. Client embeds **TWO pinned CAs**: StartCom (subj @0x14230a6cc) AND **GeoTrust** ("GeoTrust SSL CA - G2" @0x14230af10). Cert blobs are DER, referenced by pointer tables (no string xrefs). TLS impl = **Tls.cpp** funcs cluster **0x141583370–0x1415850b0** (cert-chain verify is among the big ones: sub_141583DC0/0x385, sub_141584400/0x2e0, sub_141584B10/0x2a9), **TrClient.cpp** handshake sub_141588210/sub_141587C10/sub_141588210.

**KEY PATCH INSIGHT:** forcing the STS *status* alone is useless — the client then hits the Portal HTTPS gate behind the SAME pinned cert. The real keystone single patch = **neuter TLS cert-chain verification** (accept any server cert) in the Tls.cpp cluster, THEN redirect STS/Portal hostnames→localhost and run a local HTTPS responder (STS: return success+ticket; Portal: account info). Exact verify byte-patch = next focused RE (triage the ~5 large Tls.cpp funcs for the chain-compare/return-fail branch). After STS success the client proceeds: STS→Portal(HTTPS, same cert gate)→AuthSrv login txn (sub_14023D350 result=0)→char-select.

**Consequence for emulation / "log in with test/test":** No redirect+emulator alone works. To reach a login/char-select screen OFFLINE you must patch a CLIENT-SIDE chain (classic offline-crack), each layer revealing the next: (a) force STS success (patch BindStsRequest / STS response handler to synthesize a ticket), (b) force Portal success (sub_140246C30 / GcPortal result gate), (c) feed AuthSrv login-success msg (result=0 + fabricated account + ≥1 char/world entry, def per sub_14023D350's struct: +36 result, +224 guid20, +576 count, +580 16*count) — our plaintext MsgConn emulator can send this, (d) then the client opens a GAME-server MsgConn for char-select→world (a whole second protocol + world sim). Steps a–c reach char-select with a fake account; a playable world (d) is a full server emulator (no public GW2 emu has reached this). Highest-leverage single next RE target for an offline login screen = the STS/portal success gate (force-success patch).

**CHARACTER CREATION path (can login be skipped straight into char-create?):** Char creation is a distinct **GAME_TYPE_CHARCREATE** scene. UI+3D preview are LOCAL: scene ctrl **ScnCharCreate.cpp** sub_14029B8F0–sub_14029F180; camera/doll-framing fn sub_14029D080 does pure local math from `CharCreateContext()->GetRace()` (dollax/dollay/dollaz/yaw/pitch/scale, no net). Context = **CcContext.cpp** ("charCreateContext"), widgets CharCreate{Race,Sex,Profession,Name,MadLib,Int,Btn}. BUT the client reaches it by LOADING A CHARCREATE-TYPE MAP: gameType/mapType come from mission client **MsCliApi.cpp** (sub_14140C9C0: mapType=sub_1412DBBF0(), gameType=sub_141411E70(mapType); GAME_TYPE_CHARCREATE==1). Map normally assigned by game server; map ASSETS are in the .dat (readable via gw2mcp). So offline char-create = (1) synth local login-success (0 chars → char-select, sub_14023D350 result=0), (2) force local CHARCREATE map load bypassing game-server assignment (mission client), (3) init CharCreateContext → ScnCharCreate renders interactive with 3D preview. Finalizing/creating a char (submit) needs the game server. Achievable milestone = interactive char-create screen offline; multi-patch (login + mission/map client), each bounded.
