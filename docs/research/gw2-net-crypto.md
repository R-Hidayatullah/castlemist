GW2 live-network packet crypto, RE'd from Gw2-64-disable-aslr.exe (D:\Perforce\Live\NAEU\v2 build).

**Cipher = RC4 (stream), per MsgConn.**
- PRGA encrypt/decrypt: `sub_140FE2E30` — textbook RC4 (i=(i+1)&0xFF; j=(j+S[i])&0xFF; swap; out=in^S[(S[i]+S[j])&0xFF]). State layout: a1[0]=i, a1[1]=j, a1+8 = 256-byte S-box.
- KSA (key setup): `sub_140FE30C0` — 20-byte key. base = memset0 (`sub_1409B6EE0`) XOR key20, then ONE SHA-1-style round (ROL5/ROL30 + magic consts) mixes it, then standard 256-iter KSA indexing key bytes mod 20.
- Two independent cipher states per connection: **recv @ conn+300 (0x12C), send @ conn+564 (0x234)**. Both initialized identically from same key, then each keystream advances separately. Send state copied from recv state right after KSA.

**Where the 20-byte key comes from (MsgConn.cpp `Msg::Raw::ClientRecvEncrypt` = `sub_140FDCE60`):**
- conn+264 = mode (2=CLIENT_START, 3=ENCRYPTED). Connect packet (msg id 22) carries a 20-byte nonce/salt at payload+2.
- effective key v28[20] = storedSessionKey(conn+280..299) XOR nonce20 → fed to KSA. So RC4 key = f(handshakeSecret ⊕ per-connect nonce).

**Send path (`sub_140FDDD60`, MSGCONN_MODE_ENCRYPTED):** buffers plaintext at conn+920, on flush calls `sub_140FE2E30(conn+564, len, conn+920, out)` (RC4 encrypt with send state), then ships.

**Handshake = custom TLS/RSA** (`Arena\Services\Tls\Tls.cpp`, `Arena\Services\TlsRsa\TrClient.cpp`): cipher-suite table (`m_cipherSuites`, lookup `sub_14157A1E0`), HANDSHAKE_STEP CLIENT_HELLO→COMPLETE, RSA (mpuint bignum `..\lib\rsa\mpuint.cpp`, "-----BEGIN RSA PRIVATE KEY-----"), SHA256 (`CptSha256.cpp`), HMAC (`CptHmac.cpp`). Randomness via CryptGenRandom.
- Client key-material send: `Gc::AuthSrvEncryptCallback` (`sub_140240930`, GcAuthCmd.cpp) generates two 32-byte buffers (`sub_1409CB5F0`/`sub_1409CB4B0`), sends them as MsgConn msg fields (msg types 2/3 via `sub_140FDE780`), then finalizes+switches channel to encrypted (`sub_140FDE760/750`, `sub_140239FF0`).
- `Gc::GameSrvEncryptCallback` (`sub_14023EB10`, GcGameCmd.cpp) = same switch-to-encrypted for the game-server connection.

**Message serialization (template/def-array system), all inside the RC4 stream:**
- Two-tier framing. Pre-handshake RAW: `[type:1][len:1][payload]`, dispatched via 3-entry table `funcs_140FDE5DD` (ClientRecvEncrypt/ClientRecvError/RecvInvalid). Post-handshake ENCRYPTED: bytes RC4-decrypted (`sub_140FE2E30` recv@+300), appended to reassembly buffer (`sub_140FE2B50` @conn+88), then `Msg::DispatchStream` (`sub_140FDD790`).
- DispatchStream: reads **msgId = uint16 LE** (`Msg::ReadStream` `sub_140FE2F90(buf,2,4,...)`), flood-checks, looks up `recvMsgPacked` (message def) by id from protocol registry (conn+24 → `sub_140FE1A20`), then `Msg::MsgUnpack` (`sub_140FE02A0`) deserializes fields into a C struct sized `defArray[0].defSize`, then calls handler `(*(def+24))(ctx, struct)`. dispatchType 0 vs 1 = calling-convention of handler. No per-message length prefix; sizes come from the def + self-describing var fields. Wire msg = `[msgId u16][fields per def]`.
- **MsgUnpack field type codes** (def entry = 40 bytes: [0]=type,[4]=count/max,[8]=elemSize,[3]=nested def ptr,[10]=next; 0/24=end): 1,3=int16(2B); 2=byte(1B); 5,7,0x1A=8B(int64/f64); 6,0x19,0x17=4B(int32/f32); 8=12B(vec3); 9,0xB=16B(vec4); 0xA=12B+ext(`sub_140FE0A30`); 0xC=28B fixed struct; 0xD=UTF-16 wstring(null-term, max count*2); 0xE=UTF-8 string(null-term, max count); 0xF=optional nested struct(1B present flag); 0x10=fixed array count*elem (nested); 0x11=u8-counted array; 0x12=u16-counted array; 0x13=fixed byte blob(count); 0x14=u8-len blob(max count, flag 0x10000→writes dispatch byte to a8); 0x15=u16-len blob; 0x16=invalid; 0x18=terminator. Def tables are static per-protocol (built by `Msg::MsgPack`-referencing `sub_140FDEB50`). Chat/movement/map-load = specific msgIds each with their own def array; not special-cased in transport.

**Official MP_ type names (from `Msg::MsgPack` `sub_140FDEB50` assert strings) + wireSize table `dword_1420C7FC0` (entry=[wireSize u32][checkFlag u32] per type):** 1=MP_WORD(2B),2=MP_BYTE(1B),3=MP_WORD(2B),4=nested/embedded(sub_140FDFE40),5=MP_QWORD(8B),6=MP_DWORD(4B),7=8B,8=MP_VEC3(12B),9=MP_VEC4/OWORD(16B),0xA=MP_VEC3+ext(12B),0xB=16B,0xC=28B struct,0xD=MP_STRING utf16(mem ptr8),0xE=MP_CSTRING utf8(ptr8),0xF=MP_OPTIONAL,0x10=MP_ARRAY_FIXED,0x11=MP_ARRAY_VAR_SMALL(u8 count),0x12=MP_ARRAY_VAR_LARGE(u16 count),0x13=fixed buffer,0x14=MP_BUFFER_VAR_SMALL(u8 len),0x15=MP_BUFFER_VAR_LARGE(u16 len),0x16=MP_SRV_ALIGN(invalid on cli),0x17=4B,0x18=MP_SRV_END(pads to 4B: writes `-count&3` zero bytes),0x19=4B,0x1A=8B. Var buffers 0x14/0x15 with type flag&0x10000 write first byte to out-param (dispatch/channel byte).

**Send API = `MsgConnSend` (`sub_140FDE780(conn, structSize, structPtr)`):** msgId is the FIRST uint16 INSIDE the struct (`*(u16*)structPtr`); structSize must == `sendMsg->defArray[0].defSize`. So in-memory struct = `[msgId u16][fields...]` exactly mirroring wire order. Lookup def by id via `sub_140FE1A40(conn+24, id)`. Only sends when mode==3 (ENCRYPTED) & flag&4 set.

**Server authentication (matters for server-emulation feasibility):** client ships an EMBEDDED X.509 root CA — StartCom Certification Authority (StartCom Ltd., country IL, "Secure Digital Certificate Signing"), RSA-4096 pubkey (modulus 0xC188DB09..., ASN.1 `30 82 02 0A 02 82 02 01 00…`) at ~0x1422c17c0, referenced by TLS cert-verify funcs sub_14157E560/E7D0/E860. TLS PRF in `Arena\Services\Tls\TlsPrf.cpp`. Client verifies server cert chains to this pinned root, then RSA-encrypts key material to server pubkey. Consequence: with the STOCK client you cannot impersonate the game server (need a cert chaining to that root / its private key — not available) and cannot passively decrypt a pcap (RSA-protected key exchange + continuous per-connection RC4 stream). With a PATCHED local client you can swap the embedded root modulus for your own CA + redirect endpoint → your emulator server completes handshake with your own private key (classic private-server model). Crypto/transport is fully reproducible; the real wall is reimplementing the server-authoritative game + thousands of msg defs.

**Key point for chat/movement/map:** encryption is at the CONNECTION/TRANSPORT layer (`NET_PROTOCOL_CLI2GAME`), uniform for ALL message types. Chat, movement, skills etc. are just serialized MsgConn messages multiplexed inside the one already-encrypted RC4 stream — they are NOT individually encrypted with different schemes. Map change = transfer to a new game/map server = brand-new MsgConn + fresh handshake + fresh RC4 key.
