Chat link = `[&` + base64(payload) + `]`. Two encoding systems in the client:

**Base64 substrate** (`Arena\Services\Base64\Base64.cpp`, standard alphabet `ABC…+/` at 0x14205f6a0):
- Encode core sub_140D86470 (Base64EncodeSize = 4*ceil(n/3)+1), wrapper sub_140D86950.
- Decode core sub_140D86300 (UTF-16 input) / sub_140D86190 (byte input); **DecodeSize = 3*(srcChars/4)**; 4 chars → 3 bytes. Decode wrapper sub_140D867F0 / sub_140D867D0.

**System 1 — classic links** (item/skill/trait/map/recipe/skin/outfit/coin/npc/wvw/achievement): payload = 1 header byte + little-endian ID + fields. Simple; matches the wiki spec. For "correct+complete ID" the tricky one is the **item link** (header 0x02): `02 [qty:1] [itemId:3 LE] [flags:1] {skin:4}? {upg1:4}? {upg2:4}? {nameKey:8}? {descKey:8}?` — **skin/upgrade ids are each a 4-byte u32 slot** (3-byte id + reserved zero byte), NOT 3 bytes (verified against wiki Zojja's Claymore `02 01 AA B6 00 E0 7D 0E 00 00 FF 5F 00 00 27 60 00 00` = item 46762, skin 3709, sigils 24575/24615). flags 0x80 skin / 0x40 upg1 / 0x20 upg2 / 0x10 nameKey(8B) / 0x08 descKey(8B); absent fields omitted, so walk flags to know length. Other classic types = `hdr + 3-byte LE id + 00`; coin = u32 copper; WvW = obj(3)+00+map(3)+00.

**System 2 — modern template links** (build 0x0D, wardrobe/skill-palette sets, travel/wardrobe templates): reuse the network **message-pack serializer** in `Gw2\Services\Msg\MsgConn.cpp`. Encode sub_140FE0B00, decode sub_140FE0C40 (asserts `def[0].fieldType == MP_MSGID`), driven by per-message descriptor tables (unk_1425FC690/7E0/880 — 40-byte field defs). Specialized skill/trait *set* codecs: encoders sub_1417D64D0/6700/6A00, decoders sub_1417D5FC0/61B0/6390 (base64 + MsgConn desc). This is why build/wardrobe/travel links are variable-length/complex vs classic ones.

**cntc content-map: chat-link id -> dat fileId (DONE 2026-07-15, offline).** RE'd via `CnData.cpp` loader (`sub_1412D6DD0` reads the on-disk PackContent; `sub_1412D82C0` applies fixups) + empirical validation on real cntc (Gw2.dat baseIds 6859/28901 via gw2index `container=cntc`, 32 packs total). **On-disk PackContent** (browser layout confirmed exact): PF "cntc" -> chunk "Main"; base=mainPos+16; 11 arrays `{u32 count, i64 self-rel ptr}` at base+4+i*12 = [0]typeInfos [1]namespaces [2]fileRefs [3]indexEntries [4]localFixups [5]externalFixups [6]fileIndices [7]stringIndices [8]trackedRefs [9]strings(codenames) [10]content-bytes. **Local packs have typeInfos/namespaces/fileRefs = 0** (per-type field SCHEMA is compiled into the exe, not the dat). **indexEntries = 16 B/elem**, object offset at **+4** (into content bytes). **Each content object: contentType(u32)@+16, numeric id(u32)@+20**, primary-asset fileId = the `fileIndices` reloc (u32 into content) at **object+64** (else first reloc in object). **CONTENT_TYPE_ITEM = 35** (id@+20 = API item id, VERIFIED: Basic Salvage Kit 23040 -> object present, id matches). Item's +64 asset is the item's **primary asset** = mix (empirical over 3104 items in one pack: ~44% texture/icon, ~41% MODL model, ~6% ASND, rest AMSP/AMAT) -> fileId is directly previewable in the browser. `fileIndices` slot holds a fileId index/value; browser reads it directly (local packs plaintext; some server/manifest packs are CONTENT_FLAG_ENCRYPTED but not shipped local). NOT the 2D icon exclusively -- it's whatever asset represents the item. Other content types (skin/outfit/...) use the SAME machinery (contentType + id@+20 + +64 asset) but id-offset per type not yet re-verified.

**Content types (IDA-verified, contentType@obj+16):** ITEM=35, OUTFIT=51, SKIN=66 (from `DmLayout.cpp`/`AchSlotsGrid.cpp` asserts `!=35/51/66`). Object numeric id@+20. A `SKIN` object (type 66) holds MANY fileIndices refs = its **appearance MODEL (MODL) + material/render textures + sounds** (e.g. skin 72 -> +48 tex 66165, +88 MODL 64572, +variants). ITEM(35) `+64` = the item's representative asset (MODL for equippable/tools, texture for icon-only items).

**CRITICAL (verified vs official API): the 2D INVENTORY ICON is NOT in cntc.** The API item/skin `icon` fileId (e.g. item 23040->66765, item 25709->575183, skin 72->61080) is a real Gw2.dat ATEU texture but is **never a fileIndices asset of the content object** -- item 23040's object refs only its model 41763; skin 72 refs only model+material textures, none == 61080. (61080 does appear as raw bytes elsewhere but NOT at a fileIndices reloc = coincidence.) So the inventory icon comes from the server render service / a master manifest, NOT resolvable offline from these local cntc packs. What cntc DOES give offline: id -> **appearance model + its material textures + sounds** = exactly what a 3D fashion/model preview needs (the browser's model renderer auto-loads a MODL's own textures). **Name/text (investigated 2026-07-15, largely BLOCKED offline for items):** content objects store name/desc as **textIds** (plain u32 fields; item 23040 name candidate = obj **+40** = textId 101480). textId -> strs record: base=(textId/1024)*1024, record=textId%1024; each base has 5 language strs files (see strs_textbase.csv fileId->baseTextId). Decode via `gw2_decode_strs`/browser strs. **KEY finding: item-name strs files are ~90% RC4-packed** (e.g. base 101376 files = 89/1024 confirmed) -> need per-textId keys, only ~774 captured -> **item names NOT decodable offline in general**. SKIN-name strs files are mostly PLAINTEXT (raw-utf16, e.g. base 1106944 = 320/1024) so skin names ARE offline-decodable -- BUT the skin object's exact name-textId field offset is unconfirmed (skin-72 obj field guesses decoded to unrelated skins) AND cntc skin content-id@+20 == API wardrobe-skin-id is UNVERIFIED (only verified for items). Net: reliable names/icons need the GW2 HTTP API; cntc reliably gives only the appearance model+material assets offline. **Skin RE follow-up (2026-07-15): skin names are ALSO mostly RC4-encrypted.** For skin obj id=72 (API="Reinforced Scale Pauldrons") 5 of 7 in-range u32 fields are RC4-packed; the only plaintext one (+104=textId 1073108="Bestial Tides Tattoo Legs") is SHARED across skin objs id 72/1995/11982 -> it's a pointer/shared attribute, NOT the per-skin name. Skin-name strs files are ~31% plaintext (vs ~9% for item names) but still mostly packed, and the true name field sits in an encrypted slot. Also cntc-skin-id vs API-skin-id equivalence stays unverified. Conclusion: offline names (item AND skin) are not reliably achievable with the ~774 captured keys; use the API for names+icons. The shipped cntc map already gives skin/item appearance model+textures offline (the fashion-preview core); only the name/icon labels are API-gated. Most strs text overall is plaintext (~87% in a sampled quest file) -- it's specifically the item-name category that's heavily encrypted.

Module `castlemist/{include,src}/content_map.{h,cpp}` (`gw2cmap`): `build(dat_path, cntc MftData[], progress)` decompresses+parses every cntc into `unordered_map<(u64)type<<32|id, vector<u32> fileIds>` (ALL fileIndices refs per object, cap 16); `resolve_all(type,id)` / `resolve()` (first); `content_type_for_header(0x02->35,0x0A->66,0x0B->51)`; `save/load` binary cache `content_map.bin` (magic 'GC2N', varint) next to the exe. Decoder popup **"Resolve assets via cntc"**: builds on first use (cache, else bg thread over ~32 cntc packs via `castlemist::db::query_base_ids("","cntc",...)` -> needs main Gw2.dat index loaded), classifies each fileId via `castlemist::db::lookup(get_by_base_id(fid))` -> lists them, arms **"Open model"/"Open texture"** buttons (navigate the main browser to that fileId). WM_APP_CMAP_DONE posts completion. baseId->mft index = baseId-1.
