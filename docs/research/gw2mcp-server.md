`gw2app/gw2mcp/` is a self-contained MCP server (built 2026-07-08, verified against the real 87 GB Gw2.dat) exposing the reverse-engineered GW2 tooling as Claude tools.

Architecture: heavy work stays in C++ via a headless CLI `native/gw2dat_cli.exe` (vendors gw2dat.cpp, cmp_decompress_method0.hpp, gw2_atex.hpp, BinaryParser.cpp); a thin FastMCP Python layer `server/server.py` shells out to it. 9 tools: gw2_info, gw2_list_entries, gw2_lookup, gw2_resolve, gw2_sniff, gw2_extract, gw2_decode_texture (ATEX→PNG), gw2_parse_packfile (uses templates/gw2_packfile.json), gw2_decode_strs. STRS decoding is Python (`server/strs.py`, ported from `strs_decode.py`) run over the C++-decompressed bytes.

**Two ID namespaces that collide** (source of user confusion): `baseId` == physical MFT index (used directly, `--index`/`--base-id`); `fileId` == game logical id (resolved via table). Same number is often valid as both but points to different files. `gw2_resolve --id N` shows both readings. Most hand-curated ids are baseIds — prefer base_id first.

**baseId is off-by-one from the MFT array index (2026-07, user-confirmed).** Correct data access from a fileId: fileId → baseId (lookup table) → real entry = **`mft_data_list[baseId - 1]`**. The fileId is the stable/correct locator; the baseId numbering is 1 higher than the MFT index where the bytes live. Verified: fileId 1793212 → baseId 222261 (=a MODL packfile!) but the real data (a DXT5 ATEX texture) is at index 222260 = baseId-1; fileId 3414834 → baseId 256755, real data at 256754. **Tool inconsistency:** `gw2_sniff`/`gw2_extract`/`gw2_decode_texture` apply the -1 and reach the right bytes; but `gw2_lookup`/`gw2_resolve` report the RAW baseId (no -1) — so resolve(1793212) mislabels it "MODL" (that's mft[222261], the neighbor). Fix those two tools to subtract 1. This was the cause of gw2gsviewer albedo decode `EXC`→black-silhouette for world models (slot0 read the wrong index); fixed in the shared DAT-access code.

Model pipeline (added 2026-07-08): `native/gw2model.hpp` walks GEOM chunk (ModelFileGeometryV1.meshes[]→ModelMeshDataV66.geometry→ModelMeshGeometryV1: verts{fvf,vertexCount,vertices[byte]}+indices[word]) and MODL materials (permutations[0].materials[].textures[].filename→fileId); decodes GrFvf per GW2_Vertex_FVF_Notes.md. CLI `model` command exports OBJ+JSON. Validated: vertexCount matches declared, OBJ bbox == minBound/maxBound. `viewer/gw2viewer.cpp` is a DX11 (MinGW, CINTERFACE+COBJMACROS, link -ld3d11 -ldxgi -ld3dcompiler -ldxguid) model viewer loading straight from the DAT; `--shot <png>` = headless one-frame capture. Renderer now does material-driven shading (notes sec.6 faithful reconstruction, NOT game DXBC): extractor reads full material (materialId/flags/sortLayer, per-texture token/flags/uvIndex, float4 constants) + tangent+bitangent from FVF tangent-frame. Roles by format heuristic (materialId/tokens are 0 on these legacy materials): 3DC/BC5→normal (tangent-space normal mapping), largest DXT→diffuse (tinted by constant), grayscale diffuse→effect (luminance→alpha, tint, alpha-blend, depth-write off). Verified: 291830 rock (surface, lit), 291982 billboard (surface), 291978 (effect, ethereal blended glow — was flat grey).

Game-DXBC path was investigated & rejected as multi-week: sub_1402F46E0 = 58-shader table → AMATGRMT reflection blobs in .rdata (0x141932030+, sizes+textureCount per id); actual GPU code = separate bgfx DXBC VSH/FSH blobs (location unknown), needs full bgfx+Amat runtime reconstruction (cbuffer packing, sampler binding, vertex layout). No community viewer runs game DXBC.

(superseded) Texture ROLE note.

BinaryParser `filename` decode is now byte-exact with game sub_140DAB4A0 (FileArchive.cpp:702): fileId = 0xFF00*high + low - 0xFF00FF with full validity gate; invalid→0. Also FVF vertex fields live in ModelMeshGeometryV1 (was TODO in the FVF notes).

Texture: decodes ATEX family AND CTEX/CTTX/CTEC/CTEP/CTEU/CTET — the C-variants have a byte-identical container (same fourcc+dims+mips), differ only in the 4-byte magic, so the CLI aliases C*→A* before castlemist::atex::parse (reports `aliasedFrom`). Verified visually with real CTEX icons.

Texture resolution pairs (verified against DAT): GW2 often stores a texture at consecutive MFT indices — baseId B = full res, baseId **B-1 = half res** (same format, exactly half dims). It's a frequent convention, NOT universal (some single-res; adjacent baseId can be an unrelated normal map). A fileId always maps to full-size baseId B. `gw2_decode_texture` reports `isFullResolution` + `reducedSibling{index,width,height}`.

STRS: `raw-utf16`/`confirmed` records are byte-exact real text; `packed` records are RC4-locked (keystream from runtime cross-ref state not in a standalone entry) so text is structural-only — NOT solved. Confirmed STRS sample baseIds: 2925, 2930, 632438, 635540, 2878, 2924, 3558, 156894.

**Compression/encoding (inverse tools, added 2026-07-24):** Method0 has a full ENCODER now — `native/include/cmp_compress_method0.hpp` (BitWriter mirror of the reader, meta-huffman inverse, `assign_codes` = line-for-line mirror of the decoder's canonical build so codes round-trip by construction, package-merge length-limited Huffman capped at 15 bits, hash-chain LZ77). Key gotcha: usable back-distance window is **32768 not 40960** — DIST_BASE[29]=24576 + (1<<DIST_EXTRA[29]=13) tops out at distval 32767 (indices 30/31 are 0/unused); MAX_MATCH 256 (lenval≤255), MIN_MATCH 3, minMatchAdd=1, fixed 4096-token blocks. `compress_entry` re-inserts CRC framing (inverse of strip_crc32) with **real CRC-32C (Castagnoli, reflected poly 0x82F63B78, init/xorout 0xFFFFFFFF, LE, independent per 0xFFFC chunk + trailing over final partial)** — empirically confirmed 2026-07-24 against live Gw2.dat entry bytes (crc32c(chunk)==stored word for every chunk incl. trailing); output is a byte-faithful on-disk entry that passes client checksum validation. `crc32c()` lives in cmp_compress_method0.hpp. Verified byte-identical round-trip on strs/texture/modl entries incl. a 489KB multi-chunk file (ratios 0.23–0.70). Texture encoder `native/include/gw2_atex_encode.hpp` (DXT1/DXT5 = BC1 color + BC4 alpha, bounding-box endpoints, full mip chain, **raw flags==0 plane layout** = inverse of inflate_mip's byte-aligned reads: DXT5 payload = [alpha 8B/blk][endpoints 4B/blk=offB][indices 4B/blk=offC]). Reads PNG via vendored `third_party/stb/stb_image.h`. Re-encoding a game DXT5 → MAE 0.70/channel (near-lossless), visually identical. CLI cmds `compress`/`decompress`/`encode-texture`; MCP tools `gw2_compress`/`gw2_decompress`/`gw2_encode_texture` (now 12 tools total). Both self-verify and report `verified`/`meanAbsError`.

**Why/How to apply:** Method1 delta is still not implemented (decompress OR compress). The headless build deliberately drops the GUI WIC/D3D preview path from `entry_extractor.cpp`. Build with MinGW g++ (`native/build.ps1`) — **must static-link** (`-static -static-libgcc -static-libstdc++`) or the exe fails with exit 127 (missing MinGW DLLs). Rebuild the exe after any change under `native/`. Archives: Gw2.dat at Steam path, Local.dat at `%APPDATA%\Guild Wars 2` (tool arg `local=True`). Source RE lives in sibling `castlemist/` and `minieditor/`.
